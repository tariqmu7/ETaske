# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

ETaske — a real-time enterprise workflow dashboard (correspondences → tasks → milestones → archive) for a single organization. React 19 + TypeScript + Vite SPA with a Firebase (Auth + Firestore) backend. Originally scaffolded as a Google AI Studio app; the `react-example` package name and AI Studio references are vestigial.

## Commands

```bash
npm install            # install deps
npm run dev            # dev server: Express + Vite middleware on http://localhost:3000
npm run build          # production build -> dist/ (this is what gets deployed)
npm run preview         # serve the built dist/ via Vite
npm run lint           # type-check only: tsc --noEmit  (there is no ESLint)
npm run clean          # rm -rf dist
```

There is **no test suite and no test framework** configured. Do not invent test commands; `npm run lint` (type-check) is the only verification step.

Deploying Firestore security rules is separate from deploying the app:

```bash
firebase deploy --only firestore:rules   # pushes firestore.rules to the NAMED database (see below)
```

## Architecture

### Hosting / runtime split (important)
- `server.ts` is an Express wrapper used **only for local dev** (`npm run dev`/`start`): Vite middleware in dev, static `dist/` in prod, plus a `/api/health` route. It contains **no application/API logic**.
- Production is **static GitHub Pages**: `.github/workflows/deploy.yml` builds `dist/` and publishes it on push to `main`/`master`. The Express server is never deployed. `vite.config.ts` sets `base: './'` for relative asset paths on Pages.
- There **is** a small server-side backend: **Cloud Functions** in `functions/` (codebase `etaske-functions` in `firebase.json`). `functions/src/index.ts` has two Firestore-triggered functions (`onNotificationCreated`, `onAnnouncementCreated`) that send FCM pushes via `firebase-admin` against the named DB. Deploy with `firebase deploy --only functions` (separate from the app build and from rules). These require the Blaze plan; the app does **not** depend on them — the same FCM/Telegram fan-out also runs through the free Apps Script proxy (see below), so Cloud Functions are optional.
- **PWA / installable app**: `public/manifest.json` + `public/sw.js` (hand-written, dependency-free — no `vite-plugin-pwa`/Workbox) make the site installable on desktop and mobile; `src/lib/pwa.ts` registers it from `main.tsx` in **production only** (in dev it unregisters instead, so the SW can't cache Vite's module graph or fight HMR). The install button lives in the top bar + avatar menu, driven by `src/hooks/usePWA.ts` (`beforeinstallprompt`). Two service workers coexist and **must keep separate scopes**: `sw.js` owns the app base, `firebase-messaging-sw.js` is registered at `./firebase-cloud-messaging-push-scope` — one scope holds one worker, so pointing FCM at the base would evict the shell worker and silently kill installability. Because production is the Pages **subpath** `/ETaske/`, every PWA URL must be app-relative (`./sw.js`, `./favicon.png`); a leading slash 404s. `sw.js` is network-first for navigations (fresh deploys land on reload), cache-first for fingerprinted `assets/*`, and skips cross-origin, non-GET, `/downloads/` (the 22 MB .exe) and the FCM worker. Bump its `CACHE` constant when its logic changes. Icons: `icon-192.png`, `icon-512.png`, `icon-maskable-512.png` generated from `favicon.png`.
- **Telegram notifications** (@E_TASK_bot): the client mirrors every notification to the recipient's Telegram DM through the `google-apps-script.js` proxy (`action: 'telegram'`), and that same script is the bot's **webhook** (authenticated by a `?tgsecret=` query param, since Apps Script can't read headers) for the account-linking flow. Bot token + webhook secret live as **Script Properties** (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`), never in the bundle. Users link via avatar menu → Connect Telegram (`src/lib/telegram.ts`, poll-based); the script itself saves the chat id on `checkLink`. **Contact ids are private (queue A3b):** `telegramChatId` and `fcmToken` live in the owner-only `users/{uid}/private/contact` (`src/lib/userContact.ts`), never on the public `users` doc — the client asks the script to message a person (`action: 'notify'`, `toUid`) and the script looks the ids up (`recipientContact` / `contactsFor`, falling back to old ids on the user doc until `moveContactsToPrivate()` has been run once by hand). Full setup in `TELEGRAM-NOTES.md`. This path is **free (no Blaze)**.
- **Telegram reply-to-update** (queue B5): replying **"done"** or **"delay to Sunday"** (EN/AR, many date forms) to a bot message about a task or correspondence updates it — status `Done` / `Closed`, or `dueDate` (tasks) / `deadline` (correspondences). All of it lives in `google-apps-script.js` (REPLY-TO-UPDATE section): the record is read from the **link in the replied-to bot message**, the replier from the Approved user whose private contact doc holds that chat (`usersForChat`), and the write goes through **Firestore REST with the script owner's OAuth token — which firestore.rules do NOT apply to**, so `tgCanUpdate` is the only gate and must be kept in step with the rules' update conditions (one deliberate widening: a correspondence's assignee may close/re-date it). A done task also closes its `correspondingId` letter, as the app does. The assigner + managers get a bell entry and a Telegram DM (not FCM); bids are refused. Overdue/escalation reminders carry a bilingual reply hint (`replyHint`, set in `createNotification`). Needs the `datastore` OAuth scope — see TELEGRAM-NOTES.md. Harness: `scripts/harness/telegramreply.mjs` (pure block + the whole webhook against a fake Firestore).
- **Outlook Feed** (`src/OutlookFeed.tsx`): reads the user's *local* Outlook via a Python helper they run on their own PC — `outlook_bridge/` (Flask + win32com on `http://localhost:5111`, static `X-Bridge-Token`). It serves both **Inbox** and **Sent Items** (`?folder=`; sent mail sorts by `SentOn` and carries `direction`/`recipients`). Nothing leaves the machine until the user accepts a suggestion and saves the record. The page **pulls by itself** every 2 minutes while it is open and the tab is visible (switchable, remembered in `localStorage`), and turns each new incoming mail into a **suggestion** — which record it should become, the client matched against the live bids/projects, plus a deadline and tender number read out of the text (`src/lib/mailSuggest.ts`, pure logic, harness-covered). Accepting a *task* opens the panel this page owns; a *bid* or *correspondence* is handed to its own board prefilled through `src/lib/createIntent.ts` (the same park-then-consume shape as `deepLink.ts`) — nothing is written until the user presses Save there. Accepted/dismissed items live in one localStorage ledger so a suggestion never comes back. The auto-pull is entirely client-side, so the bridge `.exe` does **not** need rebuilding for it. **Threads** (`src/lib/mailThreads.ts`, also pure and harness-covered): Inbox and Sent Items are grouped into reply chains so a three-message chain offers **one** record, not three, and the ledger is keyed by **thread**, not by message id (old per-message entries are still honoured). The bridge returns no Outlook `ConversationID` and its `recipients` are **display names, not addresses**, so the thread key is the cleaned, normalized subject and a sent mail only counts as an answer when it went back to the person who wrote in — that is what keeps two clients who both write "Monthly report" from cancelling each other out. A chain whose newest message came **in** with nothing sent back since is flagged after **2 working days** (Fri/Sat weekend, configurable), shown in a *Waiting for a reply* panel above the suggestions and as a chip on the message itself; *Follow up* opens a prefilled high-priority task. Because that flag needs what we SENT, the page reads Sent Items in the background even while the user is on the Inbox. The built `ETaske-OutlookBridge.exe` is committed at `public/downloads/` (~22 MB) so the app can offer it as an in-page download; **rebuild + re-copy it whenever `outlook_bridge.py` changes** — see `outlook_bridge/README.md` (including the `win32timezone` hidden-import trap that silently blanks all timestamps).
- Otherwise app logic is client-side. `resend`/`twilio` in `package.json` are unused (can't run from the static client). `@google/genai` / `GEMINI_API_KEY` is leftover AI Studio scaffold and is **not** wired into anything anymore (the old `vite.config.ts` `define` was removed).
- **Daily briefing** (`src/lib/dailyBriefing.ts`, pure builders + harness-covered): at most **one message per person per day** — "Good morning — 3 due today, 1 late" plus the late/today/this-week bullets (5 per section, the rest counted) — and, for a Manager/Admin, a **whole-department digest hard-capped at ten lines** (totals, the pipeline and the nearest closing bid, the longest late with their owners, the load per person, records nobody owns). It complements `src/lib/dueAlerts.ts`, which fires per record; this one describes the day. Tasks, correspondences and opportunities are flattened by `App.tsx` into one `BriefItem[]` and the briefing only runs once **all three** listeners have reported. Delivery is the normal `createNotification` path (bell + Telegram DM + FCM), with a `urlOverride` pointing at `#/due-soon` because a briefing is about the day, not one record — its `daily_briefing` type deliberately matches none of `refTypeForNotification`'s stems. ⚠ It is **client-side like every other alert here**: it is sent the first time the person opens ETaske that day, not at a fixed hour, and somebody who never opens the app never gets it. The once-a-day ledger is `localStorage` (`etaske:briefing:<uid>`, personal and manager halves stamped separately) and the day is the **local** calendar date, not UTC.

- **One-box capture** (`src/components/QuickCapture.tsx` on Home, `src/lib/quickCapture.ts` pure + harness-covered, queue task C1). The default way to add work: paste an e-mail or type one sentence ("meeting with Petrojet Tuesday about the Algeria offer, Ahmed to send prices") and the box proposes, as you type, the record type (task / correspondence / bid — the user can switch it), title, owner, date, linked bid/project and priority, with a "Why:" line quoting what each guess came from. **Review and save** opens the normal create form already filled in — the shared `CreateTaskPanel` right there for a task, or the bid / correspondence board through `createIntent` — so **nothing is written from the box**. **No AI on purpose**: the site is static and the repo is public, so a model key could only ship in the bundle; it is plain rules on top of `mailSuggest.ts` (a pasted Outlook mail — English or Arabic headers — goes through `suggestFromEmail` unchanged). Rules worth knowing: a weekday is always the NEXT one (Tuesday said on a Tuesday = a week today); "next week" = the coming Sunday, "end of the week" = Thursday; `30/9` without a year rolls to next year once passed; a dot is never a date separator (2.5 million); the earliest date in the text wins. Owner: a name followed by "to/will/should" or after "ask/assign to/على" wins, then "I will"/«سأرسل» = the writer, then the only colleague named, else the writer; a first name shared by two colleagues names nobody; only people the form's Assignee list offers (own dept + team, or anyone for an Admin) can be proposed; a small bilingual first-name table (`FIRST_NAMES`) lets «منى» find "Mona Fathy" and Tarek find Tariq. Priority: due today = Urgent, within 3 days = High, "urgent"/«عاجل» raises one step. Bids/projects come from `src/hooks/useKnownParties.ts`, shared with the Outlook Feed. Harnesses: `quickcapture.mjs` (logic) and `quickcaptureui.mjs` (browser, through to the task document written).
- **Voice note → task** (queue task C2) — a **Speak** button on the same box (`src/hooks/useDictation.ts` + pure `src/lib/dictation.ts`). The **browser's own speech recogniser** (Web Speech API — Chrome, Edge, Safari, Android; Chrome sends the audio to Google's speech service) writes into the box, **Egyptian Arabic by default** (عربي / EN switch, remembered in `localStorage` `etaske.voiceLang`); from there it is read exactly like typing, and still only fills the box. Final pieces are rebuilt into one transcript each time (`joinSegments` — Android Chrome repeats the whole transcript as every piece); unfinished words show grey under the box, never in it; typing stops the mic; no recogniser (Firefox) = no button. Spoken forms added to `readDate`, so typed text gets them too: number words → digits on the private copy only (`spokenNumbers`), Arabic month names («5 أكتوبر», «أول نوفمبر», «5 شهر 10»), «يوم 30 9», «بعد يومين», «خلال أسبوع», and the Egyptian day names «الحد/الاتنين/التلات/الأربع» — **only after «يوم» or before «الجاي»**, because each is also an ordinary word. Harnesses: `voicenote.mjs` (logic) + section [8] of `quickcaptureui.mjs` (fake recogniser, through to the task written).
- **Starting checklists** (queue task C3; pure `src/lib/checklists.ts`, UI `src/components/ChecklistPanel.tsx`). A new bid or project opens with its standard steps already in place: the create form has a **Starting checklist** picker (bids: *Full tender* 11 steps — bid bond, technical offer, pricing, price approval, sealed offer, submission… — or *Quick quotation* 4 steps, chosen from the Source until the user picks; projects: *New contract* 8 steps; or none). Steps are dated from the record's anchor — **days before the submission deadline** for a bid, **days after the start date** for a project; with the anchor still ahead a step already past is pulled to today, with the anchor itself past the real late dates stand. The list lives **on the record as a `checklist` array** (settled rule 1 — the bid card reads "4/11 steps · 1 step overdue" for free; `firestore.rules` already allow the update, nothing to deploy) and is edited on a new **Checklist** tab of the bid and project pages: tick (records who + when), add, rename, remove, re-date, top up missing template steps, "Re-date N steps from the deadline" after the anchor moves (only open template steps; hand-dated and done steps keep their dates). **Every edit is a `runTransaction` read-modify-write of the array**, so two people ticking at once cannot undo each other. Step titles are **stored in English and display-labelled** like the bid gates; a renamed or typed step is stored as typed. The five bid gates (Milestones tab) are unchanged and separate — they feed slippage analytics. Harnesses: `checklists.mjs` (logic) + `checklistui.mjs` (browser).

- **Ask-it questions** (queue task D11; pure `src/lib/askRecords.ts`, UI `src/components/AskBox.tsx` on Home under *Add anything*). "What did we send NNPC in July?" / «إيه اللي بعتناه لبترومنت الشهر اللي فات؟» is read by **plain rules, no AI** (same reason as C1) into filters — boards (letters/tasks/bids/projects), client (longest known name from bids, projects and letter senders), colleague (`findPeople`, or "my"/«مهامي» = the asker), period (named month EN/AR/«شهر 7», this/last/next week-month-year, last N days, since <month>, a bare year; a bare month is the most recent one, or the coming one when the question is about what is **due/closing**), state (open/late/done/won/lost/submitted), sent vs received — and run over the four boards the reader can already see (tasks through `subscribeVisibleTasks`, so private tasks stay private). The boards are only read once the box is focused. The answer always shows **"Understood as"** chips so a wrong reading is visible, says honestly that mail sent straight from Outlook is not in ETaske, and every row opens its record (projects just open the board — there is no project deep link). "Sent" + a client drops the letters that came FROM that client; leftover words must all match, falling back to any word with a note. A submitted bid is never "late". Nothing is written. Harnesses: `askrecords.mjs` (logic) + `askui.mjs` (browser).

- **Client file** (queue task D1; pure `src/lib/clientFile.ts`, page `src/ClientsDashboard.tsx`, view `clients`, nav Portfolio → Clients, `g k`). `#/clients` lists every client; `#/clients?c=<name>` opens one page with: **what we owe them** (open letters on their file, open visible tasks linked to their bids/projects/letters, bids still before *Submitted* with their deadline, unticked checklist steps due within 14 days — late first), **last contact** + a short timeline (letters, bid follow-ups, project updates, Outlook mail) and "our people on this client", open bids + our won/lost record, projects and every `projectContracts` row (ending within 60 days flagged amber, ended shown), latest letters, and **latest e-mails from this PC's Outlook** when the bridge is running (searched by the client name via the new shared `src/lib/outlookBridge.ts`; silent "helper not running" otherwise; nothing saved). A client is **not a collection**: it is the `client` text on projects and bids, merged by `clientKey` (case, Arabic letter variants, punctuation, «شركة»/Co./Ltd/S.A.E.) — "AGIBA" and "AGIBA Petroleum" deliberately stay two clients. A letter belongs to a client when linked to their project/bid or when `sentFrom` names them as whole words (APC ≠ CAPCO; the longest client name wins). Child collections (`projectContracts`, `projectUpdates`, `opportunityFollowUps`) and tasks are read only once a client is open. Nothing is written; no rules deploy. Project and bid pages carry a **Client file →** link; `deepLink.ts` now also opens a **project** (`type: 'project'`, consumed by `ProjectsDashboard`), which the command palette uses too. Harnesses: `clientfile.mjs` (logic) + `clientui.mjs` (browser).

- **Waiting board** (queue task D2; pure `src/lib/waitingBoard.ts`, page `src/WaitingDashboard.tsx`, view `waiting`, nav Work → Waiting, `g w`). Two columns — **Waiting on us** (open letters, open tasks, bids before *Submitted*, Outlook chains where they wrote last) and **Waiting on them** (bids *Submitted*/*Under Evaluation*, tasks/letters marked as waiting on someone, Outlook chains where we wrote last) — each row with its **age in calendar days**, longest first, amber from 7 days and red from 14. Age runs from the day a letter arrived / a task was created / a bid was entered (or announced) / a bid was submitted / the item was marked. **The one write:** "Waiting on them" on a task or letter sets `waitingOn: 'them'`, `waitingSince` (today) and optional `waitingFor` (who); "Back to us" sets `waitingOn: 'us'` and clears both. No rules deploy (no field allowlist on either collection); the button only shows to people the rules let write (`canMoveTask` / `canMoveLetter` mirror them — a letter's assignee cannot, only whoever logged it or a manager). An older task whose `statusUpdate` is "Waiting on Third Party" counts as waiting on them. Employees see only their own items; managers start on Everyone with Mine and a person picker. Outlook chains come from the local helper only when it runs, use B2/B4's overdue rules (2 / 4 working days) and honour the Outlook Feed's dismissals; a mail we sent into the blue is never chased. "Write a follow-up" on the them side opens B4's letter. Harnesses: `waitingboard.mjs` (logic) + `waitingui.mjs` (browser).
- **Deadline calendar** (queue task D3; pure `src/lib/deadlineCalendar.ts`, page `src/CalendarDashboard.tsx`, view `calendar`, nav Work → Calendar, `g l`, `#/calendar?m=yyyy-mm`). One month grid (weeks start Sunday; below 720 px it becomes a day-by-day list via `.cal-grid`/`.cal-agenda` in `index.css`) of: submission deadlines (bids before *Submitted*), decision dates (bids *Submitted*/*Under Evaluation*), `projectContracts.endDate`, `projectSubcontracts.expiryDate`, running projects' `endDate`, open tasks' `dueDate`, open letters' `deadline`. **Contracts running out** box: ends within 60 days, or ended ≤ 90 days ago with nobody renewing/closing it. **Renewed** = a later end date on a row filed under it (`parentId`) or sharing its contract number (same project), or a later row for the same subcontractor on the same project, or a status saying renewed/extended. Closed status (EN/AR) or a Completed/Cancelled project → not shown. Contracts/projects are department-wide (shown under Mine too); tasks/letters/bids follow Mine. **Nothing is written.** **Alerts:** `runContractExpiryAlerts` (lib/dueAlerts.ts) runs only in a Manager/Admin browser (App reads projects + both contract collections for them), bell + Telegram + FCM, type `contract_expiry`, `link: '#calendar'`; each step (60/30/14/7 days, the day, once after it lapses) fires ONCE per contract per end date — own ledger `etaske:contractalert:<uid>` kept 120 days, 3 per run / 8 per day. Harnesses: `deadlinecalendar.mjs` (logic) + `calendarui.mjs` (browser).
- **Documents per project** (queue task D4; pure `src/lib/projectDocuments.ts`, UI `src/components/DocumentsPanel.tsx` = the project page's **Documents** tab, page `src/DocumentsDashboard.tsx`, view `documents`, nav Portfolio → Documents, `g f`). Letters, offers, minutes, contracts, invoices/مستخلصات, reports, drawings filed against a project: kind, title, date on the document, incoming/outgoing/internal, reference number, from/to, a link **or** a file-server path, and the pasted text or main points (the search reads it). They live as a **`documents` ARRAY ON THE PROJECT DOC** (same pattern as the C3 checklist): no new collection, **no rules deploy**, and every change is a `runTransaction` re-read + one edit; `updatedAt` is deliberately NOT bumped (filing a paper is not a change to the project). Kind/direction are stored English and display-labelled. A web link must be `http(s)` (rendered as `<a target=_blank rel=noopener>`; `javascript:`/`data:`/`file:` refused); a `\\server\share` or `C:\` path gets a Copy button because a web page cannot open it. "Or upload a file" goes through the existing Apps Script Drive upload (`src/lib/driveUpload.ts`, the same endpoint the other forms use — ⚠ subject to queue task A2). The filer or a Manager/Admin may edit/remove an entry (UI rule; the rules let any Approved user update a project). The tab and the page also show, read-only, **letters linked to the project** (`correspondences.projectId`) and **task files** (visible tasks with `projectId` + an attachment or folder path — private tasks stay private). **Search** is Arabic-aware beyond `normalizeArabic`: harakat, tatweel, أ/إ/آ/ٱ, ة, ى, ؤ, ئ, Arabic-Indic digits → Latin, and the clitics «ال/وال/بال/لل/و/ب/ف/ل» tolerated; every word must match; title hits rank above ref/party/project, then body; each kind and direction answers to words in both languages («محضر» finds "minutes", «صادر» finds sent). Matches are marked in the original text (`highlightRanges` maps folded characters back). The page's project link opens the project **on its Documents tab** (`DeepLinkRef.tab`, `takeConsumedTab`, `#/projects?open=<id>&tab=documents`). Limits: 400 entries per project, 4,000 characters of text each (the 1 MiB doc cap). Harnesses: `projectdocs.mjs` (logic) + `docsui.mjs` (browser).
- **Meetings** (queue task D5; pure `src/lib/meetings.ts`, page `src/MeetingsDashboard.tsx`, view `meetings`, nav Work → Meetings, `g m`, `#/meetings?id=<id>`). One doc per meeting in the NEW **`meetings`** collection (⚠ needs the rules block in `firestore.rules` deployed — the only D-task that does): title, date/time, place, attendees (uids) + outside guests, client, bid/project link, `agenda[]` (text, notes = what was said, decision, and the suggestion `key` it came from), `notes`, `actions[]` (text, owner, due, priority, and `taskId`/`taskSerial` once made). Three steps: **Agenda** (items + suggestions from the boards: last meeting's unfinished action points — series = same title minus numbers/dates, or same bid/project — the linked bid's deadline, submitted bids awaiting decision, checklist steps due ≤14 days, open tasks/letters on the scope, attendees' late tasks ≤3 each; invitation text EN/AR with Copy + mailto), **Minutes** (notes/decision per item; "Find action points in the notes" reads lines marked Action:/إجراء: or naming a colleague who is to do something, via quickCapture's rules), **Action points** ("Create N tasks" writes real tasks — same shape as CreateTaskPanel, public, `meetingId`, the meeting's bid/project link, assignee notified, link echo — and stores the task id so none is made twice; state follows the Tasks board). Draft minutes EN/AR; on a project meeting "File on the project" adds/updates ONE `minutes` entry in the D4 `documents` array. Saves are explicit (Save bar); an update sends `deleteField()` for cleared optional keys because `updateDoc` merges. Edit = creator, attendees, managers (UI + rules); delete = creator/manager. Harnesses: `meetings.mjs` + `meetingsui.mjs`.

- **Duplicates** (queue task D8; pure `src/lib/duplicates.ts`, page `src/DuplicatesDashboard.tsx`, view `duplicates`, nav Insights → Duplicates, **Manager/Admin only** — gated in App render, TopNav, mobile More, palette). Finds records entered twice, by plain rules (no AI): **bids** — same tender/RFQ number after folding punctuation/case/Arabic digits (certain; two *named* different clients never match; placeholders N/A/TBD/0 ignored), or same `clientKey` + title word-sets Dice ≥ 0.6 + deadlines ≤ 21 days apart (or entered ≤ 90 days apart when a deadline is missing) (likely); a year in both titles that differs = never the same; at least one must be live, and live+closed is only "likely" (may be a re-issue). **Letters** — same sender key + same/near subject (≥ 0.8) within 3 days. **Tasks** (open, visible only — private stays private) — one letter turned into two tasks (certain), or same title (≥ 0.85) for the same owner or same bid/project within 7 days. **Projects** — same contract `code` (certain) or same client + name. Groups are union-find (three copies = one group), oldest first ("Entered first"). **Two people, one client**: ≥ 2 different owners of OPEN bids for one client (co-owning each other's bids = a team, no clash); "Let them know" writes one `opportunity_client_shared` notification per person (opens the other person's bid). "Not a duplicate" / "This is fine" is a localStorage ledger `etaske:dupdismiss:<uid>` keyed `<kind>:<sorted ids>` (a clash key includes the owners, so a third person joining brings it back). **Nothing is deleted or merged** — rows open their record. The **New bid form** shows an amber "already on the board" note as the title/client/tender number is typed (`findSimilarBids`; closed bids only on a shared number), with "Open it"; it warns, never blocks. Titles are not matched across languages. No rules deploy. Harnesses: `duplicates.mjs` (logic) + `duplicatesui.mjs` (browser).

- **Weekly report** (queue task D9; pure `src/lib/weeklyReport.ts`, page `src/WeeklyReportDashboard.tsx`, view `weekly-report`, nav Insights → Weekly report, **Manager/Admin only**, `#/weekly-report?w=<any day of the week>`). A ready-to-send **Arabic** report of one Sunday–Saturday week, built by plain rules (no AI) from the records: a prose summary («أنجز الفريق خلال الأسبوع 12 مهمة، واستقبل 7 خطابات…» + what is carried over + next week), then numbered sections — tasks (finished / new / open + late, the oldest late), letters (in, closed, unread, past deadline, busiest senders), bids (submitted, won/lost/no-bid/cancelled with the winner, new, deadline missed, awaiting decision), projects and contracts (latest update per project, new projects, checklist steps ticked, contracts ending within 60 days via `deadlineCalendar`), meetings (held, action points → tasks), each colleague's line, and the week ahead. Counted nouns agree with the number (`arCount`: مهمة واحدة · مهمتين · 5 مهام · 12 مهمة; accusative by default, `gen` after a preposition); every other count is a "label: number" line so nothing else has to agree. Egyptian month names, Latin digits. **Dating the past:** a task is finished on `completedAt` (only the Tasks board sets it), else `archivedAt`, else `updatedAt` — an estimate the report admits in its closing note; a Closed letter is dated by `updatedAt`, a closed bid by `decisionDate` then `updatedAt`; "open/late" is rebuilt as of the week's Saturday (or today for the current week). Default week: Sun–Tue → last week, else this week; no future weeks. The boards are read **once** per visit (`getVisibleTasks` + `getDocs` — private tasks never included; a collection the rules refuse, e.g. `meetings` before its rules deploy, is left out and named on the page), so the text never shifts under the manager's edits. The text box is editable (Undo my edits), the department name for the heading is remembered in `localStorage` (`etaske:weeklyreport:dept`). Copy / Download (.txt with BOM) / E-mail draft (`mailto:`; over ~1,900 characters it copies the text and opens a subject-only draft). **Nothing is written or sent from the app**; no rules deploy. Harnesses: `weeklyreport.mjs` (logic + Arabic) + `weeklyreportui.mjs` (browser).

- **Follow-up letters + escalation** (`src/lib/followUp.ts`, pure builders + harness-covered, queue task B4). Two halves of "a record has gone quiet". **The letter:** `buildFollowUpLetter` writes a ready-to-send chaser in **English and Arabic**, at the tone the wait has earned — polite under 5 working days, firmer from 5, a final notice from 10 — with an `internal: true` variant for nudging a colleague rather than a client. The Arabic is written as Arabic (verbal sentences, real letter openings/closings, no «تم»/«بواسطة»/«الخاص بـ») and the day count agrees with the number (يوم عمل واحد · يومَي عمل · 5 أيام عمل · 12 يوم عمل). `FollowUpLetterModal` shows ONE letter at a time, editable, with Copy and a `mailto:` draft — **nothing is ever sent from the app**: a letter going out in the user's name is their decision. It is offered on the Outlook Feed's new **"They have not replied"** panel (the mirror of B2's *Waiting for a reply*: `mailThreads.ts` now also computes `awaitingTheirReply`/`theirWaitingDays`/`theirOverdue` — WE wrote last, nothing came back, flagged after **4 working days**, with its own `chase:` ledger prefix) and in the correspondence detail modal. **The escalation:** `runEscalations` tells the manager about a record that passed its date and then sat through a **second** grace window untouched (`quietWorkingDays` ≥ 6 working days = level 1, ≥ 12 = level 2; any edit restarts the clock). A task doc keeps no history of its old due dates, so "passes its date twice" is read as two grace windows, not two literal dates. ⚠ The scan runs **only in a Manager/Admin's own browser and notifies that manager** — running it in the owner's tab would have every employee's browser notifying every manager about the same task; the owner is deliberately NOT told. Ledger `etaske:escalate:<uid>` keeps each `<id>:esc<level>` **for 120 days**, not just for the day, so a level fires exactly once; caps are 5 per run and 10 per day, longest-quiet first.

### Data layer — Firebase, all real-time
- `src/lib/firebase.ts` initializes Firebase from the committed `firebase-applet-config.json` (public web config — normal for Firebase). Firestore uses `experimentalForceLongPolling: true` **intentionally** (works around a WebSocket internal-assertion bug when many listeners hit permission-denied at once) plus a persistent multi-tab local cache. Do not "simplify" these options away.
- Firestore points at a **named database** `ai-studio-82d500c4-...`, not `(default)` — see `.firebaserc` targets, `firebase.json`, and the third arg to `initializeFirestore`. CLI rule deploys must target this database.
- Collections: `users`, `correspondences`, `tasks`, `milestones`, `notifications`, `messages` (1:1 chat). Schemas live in `src/types.ts` (the source of truth — `firebase-blueprint.json` is stale, e.g. it lists a `Member` role that no longer exists).
- Sequential serial numbers (`TK000001`, `CR000001`) are generated in `src/lib/counters.ts` via a Firestore transaction against a `--stats--` doc inside each collection.
- File attachments are uploaded to **Google Drive via a Google Apps Script web app** (`google-apps-script.js`), POSTed to `import.meta.env.VITE_GOOGLE_SCRIPT_URL`. There is no Firebase Storage usage. Editing the script requires redeploying it as a *New deployment* in script.google.com (see the header comment in that file) and updating the env var. The endpoint is deployed "Anyone" access, so every app request goes through `src/lib/scriptProxy.ts` → `callScript()`, which attaches the user's **Firebase ID token**; the script verifies it with Firebase Auth (`accounts:lookup`) and serves only an **Approved** user (or the verified admin e-mail) — `callerFromRequest()`. Per-person hourly limits, MIME/size limits, and Telegram/push only to a chat/device on a `users` doc. All uploads go through `src/lib/driveUpload.ts` → `uploadToDrive()` (never hand-roll a fetch to the script). The old `SHARED_SECRET` / `VITE_GOOGLE_SCRIPT_SECRET` is no longer checked (it shipped in the bundle); the client still sends it only for the switch-over. Test: `node scripts/harness/scriptauth.mjs`. Drive files are **private** (queue A2b): the upload is never link-shared, and every screen opens or previews an attachment through `src/lib/driveFiles.ts` (`attachmentClick()` on the `<a>`, `openAttachment()`) or `src/components/DriveImage.tsx` — the script's `download` action, same gate, only files in the ETaske folder. Never put a stored Drive URL straight into `href`/`src` without them. Old files: `unshareAll()` run once by hand. Test: `node scripts/harness/drivefiles.mjs`.

### Auth, roles, and access control
- Firebase Auth: Google popup + email/password (`LoginScreen.tsx`). On first sign-in `App.tsx` creates the `users/{uid}` doc.
- Admin identity: any **Approved user with `role == 'Admin'`** (set in the Users screen) has full admin rights in `firestore.rules` (`isAdmin()`), so a second admin can approve/promote/remove users. The hardcoded email (`tarekmoh123@gmail.com`, in `src/App.tsx` + `firestore.rules` `isAdminEmail()`, keep in sync) is only the **bootstrap**: it may create its own Admin doc and is re-granted Admin on every login, so the app can never be left without an admin. Creating a user doc as Admin stays email-only.
- Roles: `Admin | Manager | Employee`; statuses: `Pending | Approved | Rejected`. New non-admin users start `Pending` and are gated to `PendingScreen`/`RejectedScreen` until an admin approves them in `AdminDashboard`.
- **Security is now enforced server-side in `firestore.rules`** (hardened — see `RULES-NOTES.md` for the full rationale). Reads on `tasks`/`correspondences`/`milestones`/`notifications` require `status == 'Approved'`; writes are scoped to manager/admin **or** the owner/assignee/author; `notifications` are recipient-only; `--stats--` counters are increment-only and non-deletable; and self-signup/self-update cannot grant itself `Approved`/`Admin`. Role/ownership is no longer just UI gating.
  - **Deploy caveat:** rule edits only take effect after `firebase deploy --only firestore:rules` (to the *named* DB — see Data layer). If the hardened rules have not been deployed, the **live** database may still be running the old `read, write: if request.auth != null` ruleset — verify before relying on server-side enforcement.
  - **Intentional residual openness:** there is **no per-member read isolation** between Approved users (shared org board — every approved member can read all tasks/correspondences/milestones), and the `users` directory is readable to any signed-in account. Both are documented trade-offs in RULES-NOTES.md, not oversights.

### App shell & navigation
- `src/App.tsx` is the hub: it holds all top-level Firestore listeners (auth/profile, all users, notifications, due-soon alerts) and passes `{ user, appUser, projectUsers }` down as `sharedProps`.
- **Navigation is local state, not routing.** Despite `react-router-dom` being a dependency, there is no router. `activeView` (`AppView` union) switches between dashboard components; `components/Sidebar.tsx` (exported as `TopNav`) and the mobile bottom-nav drive it. Default view depends on role (managers/admins → `overview`, others → `tasks`).
- Workflow path: `CorrespondingsDashboard` (intake) → `ManagerInbox` (manager review/assign, converts a correspondence into a `Task`, linked via `correspondingId`) → `TasksDashboard` (work + milestones) → `ArchiveDashboard`. `OverviewDashboard` is the manager/admin analytics view. The big dashboards (`TasksDashboard`, `CorrespondingsDashboard`, `OverviewDashboard` ~1k–1.3k lines) are self-contained and own their own Firestore queries and modals.
- `src/NeedsYouDashboard.tsx` (view id `due-soon`, the old `DueSoonDashboard`) is the **single** "what needs me?" surface: four tabs — Due Soon & Overdue (deadlines + the manager triage queue) and Today / Yesterday / This Week (records by the local day they were created). The Home attention list, the per-board `DueSoonBanner` and the Overview "New Today"/"Due Soon" sections were folded into it — do not reintroduce a second copy anywhere.
- `src/FollowUpDashboard.tsx` is a dead stub (superseded by `CorrespondingsDashboard`) — do not add to it.

### Conventions
- Two separate `utils` modules, do not conflate: `src/utils.ts` = app domain helpers (`normalizeArabic`/`globalSearch` for Arabic-aware search, `getUserColor`, `getGoogleDrivePreviewUrl`, `isOverdue`/`isDueSoon`); `src/lib/utils.ts` = only `cn()` (clsx + tailwind-merge).
- Path alias `@/*` → project root (configured in both `vite.config.ts` and `tsconfig.json`).
- Styling is **Tailwind v4** (via `@tailwindcss/vite`, no `tailwind.config`) combined heavily with inline `style={{}}` objects and CSS custom properties (`var(--surface-2)`, `var(--accent)`, etc.) defined in `src/index.css`. New UI should match the existing inline-style + CSS-variable idiom rather than introducing a component library.
- Search inputs across dashboards run user text through `normalizeArabic` so Arabic content matches regardless of alef/ya/ta-marbuta variants — keep using `globalSearch` for filtering.
